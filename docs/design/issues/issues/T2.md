## Objetivo
Una única capa de acceso a la API v2 (`https://api.prognosports.com/v2`), tipada desde la especificación OpenAPI y validada en runtime en las respuestas críticas. Ninguna pantalla llama a `fetch` directamente: todas usan esta capa (a través de las queries de T4).

## Alcance
- **Tipos generados** con `openapi-typescript` desde `https://api.prognosports.com/openapi`. La especificación se guarda versionada en `api/openapi.json` (o `.yaml`) y el script `pnpm api:types` regenera `src/api/schema.d.ts`. Si la URL no está accesible, se genera desde la copia versionada (§24.2).
- **Cliente HTTP** (`openapi-fetch` o `fetch` propio, a decidir en la PR) con:
  - Base URL de `VITE_API_BASE_URL`.
  - Cabecera de autorización con el token de sesión (lo lee del store de sesión de T4; el formato exacto del header se confirma con el backend actual).
  - Desenvuelve el envelope `ApiResponse` `{ success, status, code, message, result }` y devuelve solo `result`.
  - Normaliza errores a una clase `ApiError { status, code, message }` con `message` en español cuando la API lo trae; si no, mensaje genérico por código (lo traduce T5/T7).
  - En `401`: limpia la sesión y redirige a `/login?redirect=<ruta actual>` (§2.8). La redirección la hace T3; aquí solo se emite el evento / se lanza un error tipado.
  - Timeout y `AbortSignal` (TanStack Query cancela peticiones).
- **Validación Zod** en las respuestas críticas: `User` (sin `hashedPassword`), `GrandPrix`, `RaceSession`, `Prediction`, `RaceResult`, `StartGridPosition`, `Driver`, `Constructor`, `RuleSet`/`RuleSetData`, `UserPoints`, `UserResume`, `Community`, `AuthToken`. Si la respuesta no valida: se registra en observabilidad (T14) y se lanza `ApiError` de contrato.
- **Saneado de datos sensibles**: el mapeo de `User` elimina `hashedPassword` antes de que llegue a cualquier store o componente (§24.8). Test que lo garantiza.
- **Discrepancias de la especificación** (§24.7): el cliente usa las rutas reales del backend y documenta cada corrección en `src/api/README.md`:
  - regeneración de invitación: `recretate` en la spec;
  - parrilla: `/gps/.../sessions/{session}/grid` (backend) frente a `/gps/.../{session}/grid` (spec);
  - `PUT /gps/.../sessions` con parámetro `session` que no está en la ruta;
  - typo `stadingsByHits` / `previousStandingsByHits` en `UserPoints`: el modelo de dominio expone `standingsByHits` y mapea desde el campo real.
- **Funciones por área** (`src/api/<área>.ts`): auth, user, communities, competitions/seasons, gps/sessions, tipps/calculations, results/grid, points/resume, circuits, drivers/constructors, rulesets, notifications, timezones. Cada función tiene tipo de entrada y salida.
- **Subida de imágenes** (perfil, comunidad, GP, circuito): helper `multipart/form-data` con validación de tamaño máximo 2 MB en cliente (§3.3).
- Se reutilizan los mismos esquemas Zod en MSW (T9) y en formularios (VeeValidate).

## Fuera de alcance

## Criterios de aceptación
- [ ] `pnpm api:types` genera los tipos sin errores desde la copia versionada.
- [ ] Una llamada a `GET /v2/gps/{competition}/next` devuelve un `GrandPrix` tipado y validado.
- [ ] Un error `{success:false, message:"..."}` se convierte en `ApiError` con ese mensaje.
- [ ] Un `401` dispara el flujo de sesión caducada (evento consumido por T3).
- [ ] Ningún objeto `User` en memoria contiene `hashedPassword`.
- [ ] Las cuatro discrepancias de §24.7 están resueltas y documentadas.
- [ ] Ningún componente importa `fetch` ni el cliente HTTP directamente (regla de lint en T8 o revisión).

## Tests
- Desenvuelve `{success:true,result:X}` → `X`.
- `{success:false,status:400,message:"Pronóstico fuera de plazo"}` → `ApiError(400, …, "Pronóstico fuera de plazo")`.
- `401` → emite `session-expired`.
- `User` con `hashedPassword` → resultado sin la clave.
- `UserPoints` con `stadingsByHits` → modelo con `standingsByHits`.
- Respuesta de `GrandPrix` sin campo obligatorio → error de contrato.
- Subida > 2 MB → rechazada antes de enviar.
